# Design Decisions

| Decision | Reason | Alternative Considered | Why This Approach |
|----------|--------|------------------------|-------------------|
| Navy, gold, and warm neutral palette | The brand needed to feel professional and premium without becoming flashy. | A brighter, more saturated palette or a dark-mode-first treatment. | Navy anchors trust, gold gives the CTA and badges a refined accent, and the warm neutral background keeps the photo-heavy pages calm. |
| Playfair Display for headings, Inter for body/UI | Real estate benefits from a stronger editorial headline voice with highly legible supporting text. | A single sans-serif family for everything. | The serif/sans pairing gives the homepage more character while keeping filters, forms, and specs easy to scan. |
| Shared property types and mock data in `src/types` and `src/data` | The project needed one source of truth for listings, detail pages, and filters. | Duplicating property shape in each page or component. | This keeps the listing flow consistent and makes it easier to swap in an API later. |
| Filtering logic in `src/lib/filterProperties.ts` | Filtering should stay testable and independent from the UI. | Handling filtering directly inside the page component. | The listing page stays simple, and the filter utility can be reused with an API or server query later. |
| `PropertySearch` as a Client Component only for controls | The search UI needs local form state and event handling, but not result rendering. | Making the entire listing page client-side. | This keeps the interactive surface small and reduces unnecessary hydration. |
| Separate `PropertyListings` wrapper | Result count, empty state, and cards belong to the presentation layer, not the form. | Putting search controls and results in one component. | The wrapper keeps responsibilities clean and makes the listing page easy to read. |
| Mobile nav as a separate Client Component | Menu toggle state, Escape handling, and body scroll locking require browser behavior. | Making the whole header a Client Component. | The header stays server-rendered while only the menu shell hydrates. |
| Detail-page gallery as the only interactive part of the property page | The image switcher needs state, but the rest of the page is static data. | Turning the full property page into a Client Component. | This preserves server rendering for the main content while still giving the gallery interaction. |
| Contact and schedule forms split by intent | A general inquiry form and a property-specific viewing form serve different user goals. | A single overloaded form with optional fields for everything. | Splitting them keeps both flows clearer and reduces the chance of confusing the user. |
| Local image assets for key listings | Remote image fetches were too brittle for the assignment environment. | Depending entirely on external Unsplash URLs. | Local SVG assets guarantee the cards and detail pages render in dev, build, and deployment. |
| A tighter homepage than the reference | The reference site is long and content-heavy. | Recreating the full marketing depth. | The assignment focuses on browse, filter, and contact flows, so a shorter homepage gets users to those tasks faster. |
